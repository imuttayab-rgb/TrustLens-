# TrustLens Marketplace v2 — Build Tracking

**Companion to [`MARKETPLACE_FLOW.md`](MARKETPLACE_FLOW.md).** That file describes the target
product. This file tracks build status against it, epic by epic, using the same Epic IDs as the
"TrustLens Software Feature Requirements & Developer Delivery Specification" (Mam Misbah,
08 Sep 2026) so status can be cross-referenced directly against that document's §9 backlog table.

**This is a separate tracking file from [`REMAINING.md`](REMAINING.md)/[`TASKS.md`](TASKS.md)**,
which track the original academic FYP scope. That scope is ~89% done and largely unrelated to
most of what this file tracks — this spec asks for a substantially larger consumer marketplace
(SafeMeet, offers/transactions, live document+face liveness, business reputation, notifications,
i18n) that goes well beyond the FYP's SRS.

**Legend:** ✅ Fulfilled · 🟡 Partial (real, but missing pieces the spec requires) · ⬜ Not started

**Verified 13 Sep 2026** via four independent read-only code audits (not commit messages, not
prior docs) — one per requirement cluster. Every row below cites the evidence.

**Read this number carefully.** ~33% is a _weighted_ score (Partial = half credit) across a spec
that is much larger than what TrustLens set out to build originally. The FYP-scope product
(README/REMAINING.md) is genuinely ~89% done and demo-ready. This file measures a different,
larger target — treat the two numbers as answering different questions, not as contradicting
each other.

**The single biggest gap, by far:** FR-08/FR-09's live document-liveness and holding-ID-challenge
identity capture (VER-03/VER-04). The current system does one CNIC-front photo, one CNIC-back
photo, one live-camera selfie (with a gallery-upload fallback the spec explicitly forbids), and a
face-similarity score — no liveness detection of any kind. This is P1 in the spec and is the
hardest, most specialized piece of engineering in the whole document (needs a liveness SDK/
provider — this is not something to hand-roll from scratch; see §"Notes on VER-03/04" below).

| **TRU-01** Trust Score integration + appeals    | P1       | ✅     | Genuinely complete and well-engineered: signals gathered from identity/phone/email/device/network/history (`SignalCollector`), async recompute on signal change (`queue.enqueue("scoring.recompute_trust_score", ...)`), model version + evidence + reason codes persisted per signal, appeal flow writes an immutable audit entry in the same transaction as any resolution.                                                    | None of substance — this is the one epic in the whole spec that's fully done as written.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**Notes on VER-03/VER-04 (read before scoping this work):** document liveness and face liveness
are specialized computer-vision problems (motion/texture/reflectance analysis, presentation-attack
detection) that production identity-verification products almost universally buy from a vendor
(AWS Rekognition Face Liveness, a KYC SDK, etc.) rather than build from scratch — see the spec's
own references [1]–[4]. Before scoping VER-03/04 as in-house engineering work, get a decision
from the client/supervisor on whether a liveness SDK/provider is an acceptable and affordable
dependency, since hand-rolling anti-spoof liveness detection to a defensible standard is a
different order of effort than the rest of this backlog.

## Suggested next steps, in dependency order

1. ~~**BLK-01 (storage URL)** and **BLK-02 (missing legal pages)**~~ — **done 13 Sep.**
2. **Next up — MKT-04 (real seller storefront)** and **LOC-01's exact-coordinate leak**: the two

   last in the spec itself — nothing here should start before Phases 1–3 are solid.
