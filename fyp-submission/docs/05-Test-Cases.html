Test Documentation

TrustLens — AI-Powered Seller Trust Verification System for Online Marketplaces

Prepared against IEEE Std 829-2008 (Standard for Software and System Test Documentation).

⚠️ Read this banner before reading anything else in this document

This document distinguishes two different kinds of "tested," and they must never be confused:

  1. Executed — automated suite. TrustLens carries a real, continuously-run automated test suite: 330 Python unit/integration tests passing, static analysis (mypy, ruff, tsc, eslint) clean, 5 architecture-boundary contracts enforced with 0 violations, and (per the project's own security pass, make prod-security) 16 of 16 automated security checks passing. E2E: 7 of 7 Playwright tests green across 3 spec files (auth, appeals, public score — 169 lines total). These numbers are measured facts from the project's own CI and task history (TASKS.md, REMAINING.md), last confirmed 22 August 2026, nine days before this document was written. They were not re-run by the author of this documentation package as part of writing it.
  2. Pending — manual test cases below. The module-by-module test cases in §4 are a test design, derived from the functional requirements in the SRS. The large majority of them have not been individually executed as part of producing this documentation package. Where a specific case genuinely was walked through with a real browser during this pass (a handful, tied to live screenshot capture), it is marked Executed with the evidence file named. Every other case is marked Pending and must not be read as a pass.

Do not present the coverage table in §5.1 as "the test suite passes." It states two numbers — specified and executed — every time, side by side, exactly to prevent that misreading.

1. Test plan

1.1 Objectives

  • Verify that the Trust Score engine computes scores correctly, including edge cases (unavailable signals, insufficient evidence, hard caps, boundary values at band edges).
  • Verify authentication, authorization, and the RBAC permission matrix hold under adversarial input (IDOR, privilege escalation, token reuse).
  • Verify the explainability guarantee: every score's breakdown is reconstructable without recomputation.
  • Verify the public API never leaks PII and behaves correctly under rate limiting and revoked keys.
  • Honestly record what has and has not been verified, so the FYP evaluation committee can calibrate confidence correctly.

1.2 Scope

In scope: functional correctness of the scoring engine, authentication/authorization, identity and contact verification flows, appeals, the public API contract, and the security controls listed in docs/15-security.md.

Explicitly out of scope for this test plan:

  • Real-world OCR/face-match accuracy. No consented real CNIC image set exists yet (tracked as P1-01/P1-06 in the project's own task list). All AI-evaluation testing described in §4.6 runs against synthetic or public-research fixtures, never real identity documents, by design (docs/14-testing-strategy.md §6, §10 — "No real CNIC images ever enter the repository").
  • Production load/performance validation. The latency targets in the SRS (§6.1) are design targets; no load test has been run against deployed infrastructure, because nothing is deployed (§11.3 of the SDD).
  • Independent penetration testing. Only automated scans (ZAP baseline, dependency audits) have run; no manual pentest was performed.

1.3 Test levels

Unit (pytest/Vitest) → Integration (testcontainers against real Postgres/Redis) → API (httpx against the live ASGI app) → Contract (Schemathesis fuzzing the OpenAPI schema) → E2E (Playwright) → AI/ML evaluation (aggregate metrics, not per-output assertions) → Security (ZAP, dependency scans, the authorization matrix test) → Load (k6, not yet run). Full shape and targets: docs/14-testing-strategy.md.

1.4 Entry / exit criteria

Criterion
Entry Feature's use case is implemented and passes local make test-unit

1.5 Pass/fail criteria

A test case passes only when the actual observed result matches the expected result exactly, including error codes and messages where specified. A case that "mostly works" or "works but with a wrong error code" is a fail, logged as a defect, not a qualified pass.

6. Defect log

Every defect below is real, found during actual development or during this documentation pass, and is reported at its real severity. Source: TASKS.md (full history) unless marked otherwise. DEF-01 through DEF-13 are already fixed except DEF-08 and DEF-09, which remain open and are also listed as honest limitations in the SRS (§6.7) and SDD (§9.3). DEF-14 and DEF-15 were found live during the production of this documentation package itself (31 August 2026) and are reported with the same honesty — see their entries for what is and isn't yet resolved.

ID Severity Description Status Remediation
DEF-01 Critical Every background job was silently discarded. The domain enqueues jobs by string name (identity.verify, notifications.send_email, etc.) to avoid importing the worker (ADR-0003); ARQ registers jobs under their Python function name by default, so none of the 7 enqueued names matched. Redis accepted every job; the worker silently dropped each with "function not found." OCR, face matching, verification emails, OTP SMS, IP enrichment, and score recomputation had never run — invisible because seed data writes scores directly to the database. Fixed 31 Jul 2026 arq.func(..., name=...) explicit naming, pinned by a test that scans every enqueue call site and fails on any unregistered name
DEF-02 Critical No authenticated page could ever render (a routing/rendering defect predating the current split). Fixed Split rendering: private pages render client-side through the token+refresh flow; the public seller page stays server-rendered against the public API
DEF-03 High The startup route guard — the mechanism meant to fail the boot on any unauthenticated route — was checking almost nothing. FastAPI 0.141 defers include_router, so the guard walked 8 placeholder routes and saw 1 real route out of 59. It would only have warned, not failed, exactly where its own docstring promised a hard failure. Fixed 22 Aug 2026 Guard now walks the real, fully-registered route tree and raises on any gap. The codebase itself was clean (0 unguarded routes) — the check, not the app, was blind
DEF-04 High Every reason shown on the public buyer page was hardcoded to the category "Identity," including phone- and email-verification reasons — on the one screen that exists to demonstrate explainability. Invisible until the page could render at all (DEF-05 blocked it). Fixed 22 Aug 2026 Public payload now carries the real signal category per row
DEF-05 High The public buyer page (/seller/{handle}) 404'd for every seller. Fixed 22 Aug 2026 New first-party internal route (GET /api/v1/public/sellers/{ref}/trust-score), anonymous, IP-rate-limited, reusing the partner API's own use case and response model rather than re-implementing the PII-free guarantee. Rejected alternative: giving apps/web its own partner API key, which would let a revoked/exhausted key take down the demo's own opening screen
DEF-06 High Three E2E tests could never have passed. public-score.spec.ts asserted the buyer page shows a score against a page that had 404'd since the spec was written; two others had drifted into Playwright strict-mode selector violations. Fixed 22 Aug 2026 All three fixed; suite is 7/7 green
DEF-07 Medium CI's Prettier formatting gate had never actually passed. ~50 committed Markdown files were never formatted (the pre-commit hook only reaches staged files, so pre-existing files were never caught), compounded by a missing cache-directory entry in .gitignore. Fixed 22 Aug 2026 Both root causes fixed; pnpm format:check clean
DEF-08 High (open) MFA is required for ADMIN/REVIEWER login but no enrollment or verification endpoint exists anywhere in the API. SECURITY_MFA_REQUIRED_ROLES looked like the control but was dead configuration — the actual check was hardcoded, so the setting could never be satisfied either way. At its worst point this made the entire admin panel and appeal queue unreachable by any account. Partially fixed 4 Aug 2026 (policy now takes the configured roles; dev environment clears the requirement) — MFA itself remains unimplemented Build the enrollment/verification flow, or formally document the omission as a pre-production blocker, before any real deployment
DEF-09 Medium (open) The admin panel is functionally incomplete. Seller search/list, seller detail, scoring-model weight editing beyond view, and the audit-log viewer are unbuilt or placeholder screens (sellers/page.tsx is a 12-line heading). Two related session-handling bugs (admin app had no real auth wired up at all; a stale cached "not logged in" state survived a successful login in both apps) were found and fixed during the same pass. Screens: open, tracked in REMAINING.md Stage 4. Session bugs: fixed Complete Stage 4 of the project plan before claiming full admin-panel functionality in any external-facing material
DEF-10 Medium Account lockout was scoped per-account only, so one IP could spray one password across an unlimited number of email addresses without ever tripping a per-account counter. Found during the 22 Aug automated security pass. Fixed Lockout is now also scoped per-IP
DEF-11 High (accepted, not a bug) The scam-listing classifier catches only 1 of 7 real Pakistani marketplace scam ads despite 0.906 F1 on its own training-corpus split. Trained on English job-advert fraud corpora (the only data available at build time) and evaluated against the product's actual target text, it fails badly — see TC-ML-04. Known, by design not yet live Deliberately excluded from live scoring until 300–500 hand-labelled Pakistani ads are collected (P7-02); this is the project's single largest open technical risk going into the report
DEF-12 Critical (build-time) The API, web, and admin Docker images could not build at all, discovered only by attempting the build for the first time. Three independent causes: uv requires every workspace member's manifest present to resolve dependencies (only some were copied into the build context); output: 'standalone' was missing from the Next.js configs the Dockerfiles depend on; the admin image's Dockerfile hardcoded the seller app's server entrypoint. Fixed 22 Aug 2026 All three causes fixed independently; images now build
DEF-13 Critical No .dockerignore existed. The build context was 236 MB and climbing (node_modules, the Python virtualenv, .next, the 50 MB ML training corpus). The real severity: .env.production — containing the database password and JWT signing key — was inside that context, meaning a COPY . . step would have baked live secrets into an image layer that survives even a later layer deleting the file. Fixed 22 Aug 2026 .dockerignore added; context reduced to 3 MB; verified no secret file is present in any built image layer
DEF-14 High (open) Simply logging in and viewing a seller's dashboard silently destroys the demo's intended LOW/MEDIUM/HIGH risk-band spread. Found live, 31 August 2026, while capturing screenshots for this documentation package. DeviceCheck.tsx posts a device fingerprint on every authenticated page load, which enqueues a real scoring.recompute_trust_score(trigger=SIGNAL_CHANGE) job (apps/api/src/trustlens_api/api/v1/routers/verification.py:365). That live recompute evaluates real signal evidence — and because the demo seed (packages/py/trustlens-db/src/trustlens/db/seed/demo.py) stores only a placeholder CNIC-front file and no selfie file for any of the three demo sellers, IDENTITY_FACE_MATCH fails for all of them, not just the one intentionally seeded that way. The hard cap this triggers overwrote all three sellers' carefully crafted LOW/MEDIUM/HIGH scores with a uniform score=25, HIGH risk, capped, confirmed directly in the worker's own log (three distinct seller IDs, identical score=25 risk_level=HIGH cap_applied=25). This is not a screenshot artifact — it is a real, reproducible write to the database triggered by the ordinary act of using the product, and it would silently sabotage a live viva demo the first time an examiner clicks into more than one seller account. Open. Demo data was manually restored to its intended values for this documentation pass using the seed module's own scoring math (see the repair script referenced in the handover), and later captures used a browser context with **/api/v1/verification/device blocked to avoid re-triggering it. Neither is a real fix. Either seed a placeholder selfie file too (so the demo accounts' identity signal genuinely passes/fails as intended), or exclude seeded demo sellers from SIGNAL_CHANGE recomputation entirely
DEF-15 Medium (transient, not a code defect) The public seller page returned HTTP 500 for a period during this documentation pass, with the page's own error body reading "Jest worker encountered 2 child process exceptions, exceeding retry limit". This is a Next.js development-server compile-worker crash, not a regression of the real P0-12 fix — the underlying GET /api/v1/public/sellers/{ref}/trust-score route this page calls was confirmed working (200, correct payload) throughout via direct API calls. Every other route on the same dev server continued to work normally; only this one route's server-side render path was wedged. Fixed for this pass by restarting the Next.js dev server; the underlying route was never broken If this recurs, it points at resource pressure on the dev machine (the whole stack — Postgres, Redis, MinIO, four apps, and repeated Playwright captures — running simultaneously for an extended session) rather than at the application code
